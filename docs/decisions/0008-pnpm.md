# 0008 — pnpm comme gestionnaire de paquets Node

- **Statut** : accepté
- **Date** : 2026-10-03

## Contexte

Le dépôt amont utilise npm : deux `package-lock.json` (racine et frontend),
`npm ci` dans le Dockerfile et dans la CI.

Deux raisons de changer :

1. **Reproductibilité** — l'ADR 0006 pose qu'il doit exister un seul
   environnement de référence. Le lock de npm autorise le *hoisting* : deux
   installations peuvent résoudre différemment à partir du même
   `package-lock.json`. Celui de pnpm verrouille toute la chaîne transitive.
2. **Coût** — pnpm utilise un store adressable par le contenu. Ici on a deux
   arbres de dépendances (racine et frontend), plus le conteneur : de la
   duplication évitable.

Le prix du changement : pnpm n'est pas installé par défaut dans l'image Node,
il faut corepack (ou une installation globale), et `node_modules` passe en
layout isolé (liens symboliques), ce que certains outillages détestent.

## Décision

**pnpm est le gestionnaire de paquets Node du projet.** Sa version est figée
**une seule fois**, dans le champ `packageManager` de `package.json` (racine
et frontend). Les `package-lock.json` sont supprimés.

- Installation via `corepack enable` : la version vient du dépôt, pas du poste.
- Verrouillage strict partout : `--frozen-lockfile` (image, CI, local).
- Les scripts du dépôt sont réécrits en `pnpm` — il ne reste plus un seul
  appel à `npm`.

## Conséquences

**Positives**

- Chaîne transitive entièrement verrouillée.
- Un seul endroit déclare la version de pnpm : l'image ne peut pas diverger du
  poste de développement.
- Store mutualisé : un même paquet n'est stocké qu'une fois entre la racine, le
  frontend et le conteneur.
- Le layout isolé rend visible les **dépendances fantômes** : un import non
  déclaré échoue au lieu de fonctionner par hasard. C'est un gain de rigueur
  immédiat.

**Négatives**

- corepack est requis (Node ≥ 16.9). Le repli est écrit dans le Dockerfile.
- Le layout `node_modules` change : un outil qui fouille l'arbre à plat peut
  dériver. Vite est compatible, build vérifié.
- Si un `package-lock.json` réapparaît, c'est une dérive : il se **supprime**,
  il ne se réconcilie pas.

## Alternatives rejetées

- **Rester sur npm** — c'est l'état actuel : lock plus permissif, et rien
  n'empêche la divergence entre l'image et le poste.
- **Yarn** — même qualité de lock, mais migration sans gain pour nous, et
  outillage moins bien intégré à corepack dans notre configuration.
- **Un workspace pnpm unique (racine + frontend)** — plus élégant à terme : un
  seul `install`, un seul lock. Mais cela change la structure du dépôt amont,
  alors que `pnpm --dir frontend` atteint le même résultat aujourd'hui. À
  reconsidérer si la duplication se fait de nouveau sentir.
- **Bun** — un install plus rapide, mais un runtime *et* un installateur :
  hors sujet pour un dépôt dont le frontend tourne déjà sous Node.
